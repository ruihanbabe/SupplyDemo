# SupplyAgent 功能需求与业务规则

> **文档契约** · 类型：需求 SSOT · 读取：实现或评审相关 Feature 前按编号读取
> 更新：可观察的产品行为或业务规则发生变化时
> 独占：FR、BR 及其边界
> 不收录：架构实现、接口字段、验收结果和开发进度

## 1. 适用范围

本文定义“元件供应风险主动预警”MVP。一次业务闭环以一个 Run 为边界：

1. 由用户提交的业务事件唤醒监测对象；
2. 并发采集多源观察（分销商库存报价、制造商官方资料）；
3. 与阈值和上一状态差分，按去重规则产生或关闭告警；
4. 围绕告警生成决策支持：比价建议、官方推荐替代、多候选对比；
5. 在信息不足或发生外部写操作前等待人工；
6. 中断或重启后继续同一 Run，并保留完整审计。

元件适用性判断、通用问数、通用供应商搜索、库存周转监控、物流异常监控、自动下单和通用知识库不属于本期范围。

## 2. 功能需求

### FR-01 · 纳入监测与创建 Run

- 用户可纳入监测对象（元件或 BOM 行）并设定阈值与触发策略。
- 用户可通过结构化输入创建一组物料需求，并提供项目、时间窗口及可选备注。
- 事件入口与请求入口必须创建语义相同的 Run；系统必须返回稳定的 demand_id 与 run_id。
- 相同业务请求是否复用既有 Run 由幂等键判断，不能只比较自然语言。
- 输入缺少可安全推断的字段时进入人工补充状态，不得编造。

### FR-02 · BOM 展开与缺口计算

- 系统必须选择适用且有效的 BOM 版本，将需求汇总到规范化料号。
- 缺口计算、可用量、MOQ、包装倍数和数量取整由确定性业务核完成。
- 每个结果必须记录输入快照、规则版本和计算版本。
- 未取得或未验证的数量使用空值或明确的 unknown 状态，不能用 0 代替。

### FR-03 · 多源库存与报价观察

- 系统为监测对象并发查询多个分销商；各源结果独立保存与呈现，不取平均、不隐藏分歧。
- 每条候选或报价必须保留供应商、料号匹配、数量、币种、价格、交期、MOQ、观察时间和来源。
- 缓存、样例、重放和真实来源必须显式区分。
- 过期或字段不足的证据可以展示，但不能静默参与最终推荐。
- 某一来源失败不阻断其余来源；失败、超时与“该来源无此料”是三个独立结果。

### FR-04 · 供应风险与器件生命周期调查

- 系统可调查器件生命周期、停产与变更公告、供应商身份与授权关系，以及与当前交付相关的公开风险。
- 生命周期结论必须引用制造商官方资料，不得以分销商字段替代。
- 型号到官方文档的寻址必须输出 `resolved` / `ambiguous` / `unresolvable` 三态；寻址失败、文档无文字层、型号不在文档中是三个独立结果，不得合并为“查无此项”。
- 文档型证据必须记录文档修订标识、页码与原文片段；原文片段须在记录的定位处逐字命中。
- 每项 RiskFinding 必须引用 Evidence，并说明风险类型、严重度、适用对象、时间、置信度和建议动作。
- 无充分证据时必须给出“无法判断”以及需要补充的信息。
- 系统不得生成脱离当前监测任务的通用供应商画像或无依据综合评分。

### FR-05 · 生成版本化补充建议

- 建议必须列出每个缺口物料的推荐候选、建议数量、预计金额、时间信息、证据引用、风险和未决问题。
- 数量与金额来自确定性业务核；模型只负责有 schema 约束的解释、归纳和建议文字。
- 每次关键输入、规则、报价或人工选择变化都生成新版本。
- 系统必须能解释新旧版本之间的变化。

### FR-06 · 人工补充、选择与评审

- 信息不足、候选冲突、证据过期或风险不可接受时，Run 进入人工等待状态。
- 人工输入必须记录操作者、时间、问题、可选项、选择和备注。
- 用户可批准、拒绝或要求修订当前方案；审批只对指定版本有效。
- 人工决定恢复同一 Run，不创建一条与原任务失联的新流程。

### FR-07 · 创建外部采购草稿（延期）

- 经批准后，系统可将当前方案映射为目标采购系统的草稿。
- 写操作必须经过权限门、使用 logical_action_id，并在重试或恢复时保持幂等。
- MVP 首个目标系统和上线范围为 `TBD`；在确定前只允许生成内部草稿或导出预览。

### FR-08 · 事件触发

- 提交 BOM、需求或元件清单即触发调查，系统主动暴露用户未问及的问题。
- 事件入口与人工入口必须使用相同的计算、调查、审批和审计语义与权限。
- 同一对象在去重窗口内已有活动 Run 时，不得创建第二个 Run；新触发并入既有 Run 或被显式丢弃并留痕。
- 触发失败不得静默；连续失败必须可见，并按退避策略重试而非紧循环。
- **不做定时巡检。**触发源限于用户提交的业务事件，去重窗口见 Q-06。

### FR-09 · 暂停、恢复与重放

- Run 在进程重启、临时工具故障、模型故障和人工等待后可恢复。
- 已成功且仍有效的确定性步骤或工具调用不得因恢复而重复产生副作用。
- 每次模型调用必须记录 backend、model、上下文清单、工具事件、输出 schema、用量、延迟和错误分类。
- Replay 模式必须能在不访问真实模型或外部供应商的情况下复现已记录事件，用于回归和诊断。

### FR-13 · 请求路由与责任分派

- Supervisor 按请求复杂度条件路由，不是每次都执行全部 Worker。
- Worker 以可调用工具形式被唤起；Worker 之间只传类型化结果，不以自然语言段落互相协商。
- **路由失败必须退到最简链路**（Intake → Internal → Report），不得报错终止。
- 每次路由决策必须可审计：记录判定依据、选中链路与被跳过的 Worker。

### FR-14 · 业务术语与指标解析

- 业务术语由冻结的指标注册表定义，不由模型即兴解释。
- 指标解析是从注册表中**选择**，不生成 SQL；未命中返回 `unknown_metric` 并转人工。
- `MOQ`、`MPQ`、`SPQ` 等易混术语必须是独立指标，别名互不通用。
- 口径变更走版本化，保留生效时间与修改人；历史结论仍指向其当时的口径版本。

### FR-15 · 确定性快路径与 Agent 兜底

- 确定性路径优先；无法判定时抛出 **typed ExceptionCase**，例外类型是枚举而非自由文本。
- Agent 仅在例外发生时被唤起，不得进入主路径。
- Agent 无法解决的例外必须升级人工，不得自行放宽判定条件。
- 每次由 Agent 解决的例外必须留痕：例外类型、经手 Agent、判定依据与所引用的 Evidence。

### FR-11 · 告警的产生、去重与关闭

- 告警由确定性规则从观察与上一状态的差分中判定；阈值来自版本化配置，不写进 prompt 或节点。
- 每条告警必须指向触发它的观察；无观察支撑不得告警。
- **同一监测对象的同一告警类型，同时最多存在一条活动告警。**重复触发只更新证据与最近确认时间，不新建。
- 状态回退到阈值内或恢复在产时，必须关闭告警并留痕，不得静默消失。
- 告警必须记录首次发现时间、最近确认时间与当前状态，三者不得互相替代。
- 采集失败不得产生告警，也不得关闭既有告警；失败只影响“最近确认时间”。

### FR-12 · 决策支持报告

- 库存告急告警派生比价建议：按缺口数量计算各源金额，含 MOQ 与订购倍数，未知不补零。
- 停产告警派生官方推荐替代：替代型号必须来自制造商官方资料并带原文定位。
- 多候选行可输出官方资料层面的差异对比。
- **系统不出具适用性或技术等价结论**；对比只陈述官方资料怎么说，换料判断属于用户。
- 报告版本化；关键输入、证据或人工选择变化即生成新版本，并能解释新旧差异。

## 3. 业务规则

### BR-01 · 数量语义

需求量、库存量、在途量、缺口量和建议采购量必须使用明确单位与 Decimal 语义。未计算或未核验值不得写为 0。

### BR-02 · BOM 选择

系统只使用在需求时间窗口内有效、状态可用且能唯一确定的 BOM。无法唯一选择时进入人工补充。

### BR-03 · 需求汇总

同一规范化料号的需求按业务范围汇总，并保留从汇总结果回溯到原需求行的关系。

### BR-04 · 缺口计算

缺口计算公式和可用库存口径由版本化业务规则定义。计算结果不得直接修改库存或在途数据。

### BR-05 · 建议不等于占用

生成缺口快照或建议方案不会预留库存、创建采购单或承诺交期。

### BR-06 · 报价与金额

候选价格必须按满足建议数量的 MOQ、包装倍数和阶梯价计算。币种不一致且无经核验汇率时不得汇总为一个总金额。

### BR-07 · 候选选择

候选选择使用版本化规则，至少考虑数量覆盖、价格、交期、证据新鲜度和已证实风险。模型不得私自覆盖硬约束。

### BR-08 · 方案版本与审批

方案内容、输入引用和规则版本共同生成内容哈希。关键内容变化后，旧审批自动失效。

### BR-09 · 拒绝与超时

拒绝必须记录理由。人工等待超时后的动作由业务配置决定；在策略未确定前保持等待，不自动批准或执行。

### BR-10 · 部分可用

部分物料缺少候选时可以生成部分方案，但必须标记为未就绪，不能把缺失行从结果中省略。

### BR-11 · 副作用幂等

任何外部写操作以 logical_action_id 标识。相同动作重复提交时返回既有结果，不能创建重复草稿、工单或通知。

### BR-12 · 证据来源与新鲜度

Evidence 必须包含来源类型、定位信息、取得时间、查询参数摘要、内容摘要和有效期判断。新鲜度阈值来自配置或业务规则。

数值型证据（分销商响应）以时间窗口失效；文档型证据（制造商资料）以文档修订失效。两者不得混用同一套新鲜度判断。

### BR-13 · 上下文可重建

ContextBundle 由权威业务状态、有效 Evidence、Artifact 和必要人工输入编译。其 manifest 必须足以解释使用了哪些内容、版本及裁剪策略。

### BR-14 · 模型后端语义

业务节点依赖统一 ModelBackend 契约。后端切换不能改变结构化输出 schema、工具权限、证据要求和审批边界；不支持的能力必须显式失败或进入已声明的降级路径。

### BR-15 · 告警唯一性

同一监测对象的同一告警类型，同时最多存在一条活动告警。重复触发更新既有告警的证据与最近确认时间，不产生新告警。告警的关闭必须由状态回退触发并留痕，不得因采集失败而关闭。

### BR-16 · 多源分歧不合并

多个来源对同一事实给出不同答案时，必须各自保留并显式呈现分歧。系统不得取平均、取最新、取最优或任选其一作为唯一结论。需要单一取值时，由人工选择并记录选择者与理由。

### BR-17 · 事实值不得由模型产生

数量、金额、库存、交期、日期、型号与状态枚举一律由确定性代码从 Evidence 取得，模型输出 schema 中不设这些字段。数值型须能回指工具响应字段，文档型须在记录的定位处逐字命中原文；任一不成立则该次模型输出整体作废，不做纠正后采纳。

### BR-18 · Agent 不在主路径

Agent 只能由确定性路径抛出的 typed 例外唤起。任何让 Agent 直接承担常规判定的实现都违反本规则——常规判定必须有确定性实现，Agent 只兜它兜不住的部分。

### BR-19 · 指标不得由模型定义

业务术语的口径只能来自 `metric_definition` 注册表。模型可以选择指标、填充参数，不得生成或改写口径表达式。未命中注册表即 `unknown_metric`，不得以近似指标替代。

### BR-20 · Worker 间只传类型化结果

Worker 之间的输入输出必须是类型化对象。不得以自然语言段落传递业务事实，不得让下游 Worker 从上游的说明文字中重新解析数值或状态。
