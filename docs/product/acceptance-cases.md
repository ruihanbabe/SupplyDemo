## 1. 判定原则

业务硬规则由独立断言判定；语言表述使用证据覆盖和人工复核，不让 LLM 单独裁定权限与写入正确性。模型不得看到隐藏预期答案。

真实数据可作为开发集，保留独立变体作为留出集，避免仅背诵当前的 121 条用料行与 148 个候选。开发集与留出集的评测拆分报告；网络变化场景与固定离线回放分开报告。

每例需保存：`case_id`、类型、所属验证层级、来源文件哈希、记录 ID、前置条件、触发输入、故障脚本、`expected_state`、`required_evidence`、`forbidden_actions`、副作用计数、预算、判定器版本。下述用例尚未物化为完整 fixture。

**硬门禁**：固定案例的越权写入、重复草稿、伪造身份、无证据关键结论均为 0；所有硬案例必须通过，不因平均质量分抵消失败。硬门禁在四个验证层级都适用，不因层级低而豁免。

其余回答质量、引用准确率、成本、工具次数、延迟按案例分别报告，样本小不外推生产收益。性能、模型预算、延迟和恢复时间先测基线后定量冻结，不预先编造成功率或收益。

单 Agent 和多 Agent 使用相同工具、数据、预算与任务集，重复执行并报告方差及失败例；不预设多 Agent 一定更优。

## 4. 外部接入的完成证据

以下是「接入完成」的判定标准，不是用例；对应 ③④ 两层。

**每个供应 adapter**：一条已知型号、一个无结果、一个歧义样本；身份／包装／单位映射正确；限流和超时离线测试；日志不含 token/key；缓存键隔离地区与账户价格范围。

**MCP**：目标客户端实际 `tools/list` 与 `tools/call`；合法与非法输入；预算／权限执行；HTTP／进程失败恢复；协议版本兼容。只通过 REST smoke 不算 MCP 已接入。

**业务写入**：审批前拒绝、批准后草稿读回、重复动作、响应丢失核对、并发副作用计数。先验证本地可控服务，不对供应商线上接口压测或注入故障。

**端到端出口**：必须有一个固定端到端任务完成真实业务 API 的草稿创建和读回；供应查询须有授权实测记录，模拟演示不得冒充真实供货。必须覆盖：审批前写入被阻止、审批失效、重复触发、写入响应丢失、重启恢复、预算耗尽。
