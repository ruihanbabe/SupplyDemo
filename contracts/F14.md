# F14 Contract：反馈与升级

> 状态：已写，按用户 2026-09-29 授权直接实现、事后统一验收 ｜ 类型：深度② ｜ 里程碑：M3 ｜ spec：§5.7、A1 ｜ 依赖：F06、F09、F10

## 目标
反馈与重规划时机由代码决定（spec §5.7）：信号变成统一的代码卡片（只给事实与合法下一步），按分级决定立即唤醒 / 整批汇总 / 只记录；预期与实际的偏差由代码发现；满足条件时代码强制升级给人并关闭案子。

## 做什么（`src/feedback/`，配置 `config/feedback.yaml`）
1. **反馈卡片**（`cards.py`）：对案子内的信号事件（门控拒绝、失效通知、供应冲突、偏差、子任务未完成 / 失败、人工决定）生成 `feedback` 事件，`text` 为固定格式卡片：`【类型】对象` / 发生了什么 / 影响（本案 Artifact 最新版本里哪些已失效、哪些仍有效）/ 可选下一步（按类型配置）/ 需要重规划：是|否。不用 LLM、不含堆栈与模型自评。F16 的"新反馈"分区原样展示。
2. **重规划分级**：配置表把信号类型分为 必须重规划（门控拒绝、失效通知、偏差、冲突、目标修订确认）/ 汇总通知（子任务结果）/ 只记录；"必须"级唤醒案子（经 F10 路由，每日一次），汇总级只进卡片。
3. **预期与偏差（A1）**（`deviation.py`）：预期取自本案提交采购单所依据的草稿（`eta_day`）。每日代码比对：运单预计到货日晚于预期、或过了预期日仍未到货 → `deviation`（迟到）；采购单已到货但该料缺口仍在 → `deviation`（缺口未归零）。同一采购单同类偏差只报一次。
4. **代码强制升级**（`escalation.py`）：规则——同一料号在门控拒绝后又重规划 ≥ 配置次数（默认 2）仍被拒；无可行对策（某目标料的最新决策三家都无可行报价，或该料全部有效验证报告为 C 级）；关键参数来源冲突无法化解（`source_conflict` 事件，B2）；检测到疑似注入（B1，另写 `maintainer_flag`）。预算触顶沿用 F09。升级 = 写 `escalated`（规则、原因、证据引用）+ 给采购员的 `human_request`（代码摘要，Explainer 归 F23）+ 以 `escalated` 关闭案子。
5. **升级工具**：编排控制新增 `escalate_to_human(reason)`（R0，任何模式可用，理由必填），走同一升级路径并结束本段；活跃段结束时若案子已关闭则不再迁入等待。
6. **接入**：F10 `CaseRouter` 每日调用：偏差检测 → 强制升级检查 → 为新信号生成卡片 → "必须"级加入唤醒；门控拒绝事件补 `mpn` 字段（升级规则按料号计数）。
7. **消融开关**：`feedback_cards`（false 时不生成卡片，F16 回到原始事件 JSON）、`deviation_feedback`（false 时不比对预期，A1 对照）、`forced_escalation`（false 时只保留预算触顶，其余升级规则不生效）。

## 不做什么
- Explainer 生成升级摘要（F23）、Web 上的升级处理（F25）、失败后的自我复盘（spec §5.7 明确不做）。
- 重试 / 熔断 / 降级（F15）；B2 冲突检测本身（F07 已有警告函数，参数 Server 在 F19/F23）。
