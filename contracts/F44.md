# F44 Contract：业务动作授权——角色到 capability 的 API 命令门禁

> 状态：进行中｜类型：最小｜里程碑：M1｜spec：§2.1、§3、§5

## 目标

将 F31 已有的 `organization_member.role` 与 Python `ROLE_CAPABILITIES` 映射从会话展示变为真实业务命令门禁；不改变组织隔离的 PostgreSQL RLS 边界。

## 范围

- F39 的 Case、库存、需求、到货四类人工事实写入均要求 `supply:propose`。
- API 必须在已验证 actor、已选择 organization、已建立 F31 request context 的同一事务内读取成员角色并作 capability 检查。
- 角色能力不足返回稳定的 HTTP 403 `capability_forbidden`，并且不得调用供应链 Repository。
- 允许 `supply:propose` 的现有角色为 `organization_admin`、`buyer`、`hardware_engineer`；其他当前角色维持供应读取或其既有能力，但不能录入上述 F39 事实。
- 离线测试覆盖允许角色写入、只读角色拒绝全部四类写入口，以及缺 capability 时 Repository 零调用。

## 非范围

- 不新增 PostgreSQL schema、migration、RLS policy 或数据库业务角色；`supplyagent_api` 仍只是 Python 的技术数据库角色。
- 不把前端隐藏/禁用控件当作授权机制；前端体验调整以后再做。
- 不实现仓库、业务线、客户、项目、料号族或 Case owner 的 scope。
- 不实现个人例外授权、可配置角色模板、短期 capability token 或 Agent/Worker 写入能力；这些需要独立 Contract。

## 安全边界

```text
Bearer token → actor
  → F31 组织成员/RLS 上下文
  → 同一事务读取 organization_member.role
  → Python capability 检查
  → F39 参数化 DML
  → PostgreSQL RLS 最终限制 organization + membership
```

业务 capability 不能扩大组织权限：即使某角色拥有 `supply:propose`，也必须先通过 F31 成员关系和 RLS；浏览器、模型和 Worker 没有 F39 直接写入路径。
