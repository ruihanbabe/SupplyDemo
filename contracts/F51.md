# F51 Contract：声明式工具、统一执行与有序批次调度

状态：2026-10-27 P1–P4 均已实现并通过本地/克隆验证，awaiting_acceptance，等待用户验收。业务库未应用 0030/0031。下文分阶段记录保留当时证据与状态，当前结论以最终记录为准。

## 目标与依据

在保持 F36/F45 业务产物、权限及 Mission 分支策略的前提下，将工具定义、执行、批次调度分离，先统一串行路径，再开放连续兼容组并行。采用用户提供的 PilotDeck 机制调整方案；不移植其“安全调用全量前移”策略，也不以本 Contract 声称重新验证了 PilotDeck 上游。

架构权威：[spec §2.7](../spec.md#27-工具提案与副作用)；业务策略：[BL12](../business-logic.md#bl12-工具绑定执行与失败策略f51-目标)；身份、状态及数据追加：[DC15–DC17](../data-contract.md#dc15-工具定义绑定与执行身份f51-目标)。

接口、算法和源码迁移落点：[Python 工具设计](../src/product_api/TOOL_RUNTIME.md)；批次封口、所有权和版本兼容：[Pi 协议](../pi_sidecar/TOOL_PROTOCOL.md)。声明/绑定、统一 Runtime、连续兼容组 Scheduler 与 v2 桥接均已落地；生产 Worker 固定 v2，v1 仅保留显式兼容回归。

## 范围与组件准入

- ToolRegistry：声明、版本、精确别名、冲突、可用性与 Schema 投影。
- ToolRuntime：准备、执行时重验、领域 Adapter、结果持久化和稳定错误。
- ToolScheduler：串行基线、连续兼容组、顺序屏障、资源准入及取消传播。
- Pi 桥接：完整模型批次提交、原位置关联与结果消费；Python 独占执行调度。

必要性：改造前 `harness.py` Registry 同时执行工具，sidecar 手写 Schema，F36/F45 包装重复且结果落点不同。最小路径是先统一声明与串行执行；在此基线上添加 Scheduler，比立即全量并行更容易验证和回退。替代方案“保持现有包装，仅 Pi 开 parallel”不能保证 Python 顺序屏障、资源容量和统一错误。

成本：三个进程内模块、一个版本化桥接协议、DC16/DC17 的两项持久记录；复用现有 PostgreSQL、Worker、领域 Adapter、Artifact/Observation，不增加服务、SDK 或依赖。资源容量与调用记录只在对应单元追加迁移，业务库应用仍须确认精确清单。消融：在 v2 桥接和完整 Runtime 下将 Scheduler 注入串行策略，保留权限、持久化和协议语义；不是降级绕过门禁。

范围之外：R1/R2 执行、审批/渠道、MCP/Skills 动态加载、通用 Hook/参数改写、Shell/任意文件权限、动态业务依赖图、Context/Mem0、模型选型与付费调用、自动网络重试、从 Pi 内存恢复，以及完整 Provider 调用即时撤销。工具并行不提供一致数据库快照。

## 验收矩阵

1. 声明与绑定：注册名/别名精确解析，重名或跨命名空间冲突启动失败；模型只见绑定子集，未知名无模糊修复；无参数工具拒绝额外字段；可信执行声明不能由 MCP 提示或模型覆盖。
2. 执行门禁：同组织越权、跨组织、撤权、Case/BOM 改绑、Job owner/generation/lease 失效、取消和截止均测试；排队后执行前以及持久接受前重验。权限/租约失败不变成可修正模型错误。
3. 证据与错误：正常空结果是 unknown；服务失败不伪造证据；参数错误可在预算内以新 ID 修正；协议错误/重复 ID/落库失败终止。F36 Citation 仍指 Artifact，F45 仍指 Observation；错误记录不能冒充事实引用。
4. 调度：非兼容项为屏障，连续组每对调用均兼容；共享不可重入连接串行；资源等待不越过屏障；同 Trace 追加由已有串行写入路径管理；乱序完成按原位置归位。
5. 容量与恢复：跨进程原子准入、固定锁顺序、过期 owner 拒绝提交；占用超时不证明远端停止。旧 generation 不重放结果，新 generation 重新调查，不保证外部 exactly-once。
6. 桥接：版本/字段/大小/序号、批次完整性、重复/遗漏/迟到结果、流中断、超时/取消、Pi 本地拒绝与 Python 结果归一均测试；不能依据事件到达时间猜批次。v1 不支持并行，v2 不静默降级。

## P3 实施记录（2026-10-27）

Scheduler 提供 serial 消融和 contiguous 连续兼容组；全批准备后才执行，双方声明兼容且无共享互斥 session 才可重叠，拒绝项和非兼容项形成屏障。结果始终按原位归还；失败取消兄弟并等待清理，等待中重验租约、取消与截止。七项现有只读 Adapter 各自取得连接，Trace 写入仍复用原锁，明确允许 overlap；资源容量与 overlap 独立，当前没有真实外部供应商连接或配额。

## P4 实现与选型（2026-10-27）

- 生产 Worker 固定 JSONL v2；完整 assistant message_end 同步安装全部调用槽后只提交一个批次。streamFn 的实际请求 key 绑定最终消息，保留 Responses 复合 ID。Python 校验版本/序号/批次/index/ID/预算后全批 prepare；Python 唯一调度所有者，Pi sequential 只等待并消费缓存结果。
- 异步 convertToLlm 等待完整 Python 结果，验证每个位置恰好一个 toolResult，再替换内容/isError；未知工具和 Pi 本地参数拒绝同样进入 Python 受限反馈，可用新 ID 修正。没有等待所有 execute 回调的死锁条件，没有 Pi/Python 双重调度。
- 结果与台账引用在同一接受事务提交，引用的 invocation/call/batch/index 必须一致；返回正文与接受正文一致，按原用户在接受及整批交付前重验来源。旧 generation、撤权、改绑、失租、协议错误与落库失败停止当前路径。
- P3 收尾补齐受控续租及失败隔离；配置在创建 v2 Adapter 时冻结，实际策略 schemaVersion/strategy/configurationHash 登记 input_context 与调用 scheduling_snapshot。没有新增 Provider/数据库连接器或依赖，Pi 仍锁定 0.73.1。

选型理由：复用 Pi 的公开 Agent.subscribe、tool.execute、异步 convertToLlm 和现有 JSONL 子进程，保持 Pi 消息循环与 Python 业务权限/SQL 持久化各自所有权。相比在 Pi 开 parallel，Python 能同时执行屏障、共享容量和结果接受；相比重写 Agent loop，保留原生 Responses/GLM 转换及既有回归。

容量物理实现细化为按 execution/resource 的加权占用行，DC17 已同步，避免预建 N 条空槽；固定序原子锁及 held/quarantined units 总和仍保证容量。过期仅隔离，不提供未知真实远端状态的自动恢复。

明确限制：完整 JSONL 上限仍 16384 字节，单批/turn 最多16项。请求超限不执行；结果超限可能已经保存，随后不交付、不截断、不自动重执行。正向业务克隆使用一个有界供应批次三调用，其他大证据单调用；另有整批大证据超限的持久化/无后续模型请求回归，不能据此声称任意大小批次都可成功。
