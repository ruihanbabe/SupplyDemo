# F17 Contract：可观测计量

> 状态：已写，按用户 2026-09-29 授权直接实现、事后统一验收 ｜ 类型：最小 ｜ 里程碑：M1 ｜ spec：§5.11 ｜ 依赖：F07、F08

## 目标
在事件日志之上补计量：每次 LLM / 工具调用一行计量（与事件序号关联），能按案子、按运行汇总，能给出配额面板数据，并能在启动时从计量重建 Redis 配额计数（spec §5.1）。

## 做什么（`src/observability/`）
1. **计量记录**：`Meter.record_llm` / `record_tool`，由 F08 `ModelAdapter` 与 F07 `ToolProxy` 通过可选的 `meter` 参数调用（不传即不计量，不改变原行为）。字段：运行、事件序号、类型、案子、模拟日、真实日期、端点 / 提供方、模型、输入输出 token、耗时、是否命中缓存、实际扣了配额的提供方、错误类型、是否修复 / 降级。真实耗时只在这里，不进事件哈希链。
2. **上下文快照**：不另存副本——`llm_call` 事件里已有完整请求（即当时组装的上下文，spec §5.9 分区由 F16 写进请求的元数据）；提供 `context_snapshot(seq)` 按事件序号取出。
3. **案子汇总**：LLM 调用数、token、修复 / 降级次数、工具调用数、缓存命中、各错误类型次数、重规划次数（进入"规划中"的次数减 1）、升级次数、打扰人工次数（`human_request` 事件）、违规次数（`violation` 事件）。运行汇总另附 F03 环境结果指标。
4. **配额面板数据**：按真实日期、提供方汇总当日用量，并给出与配置上限的剩余量。
5. **配额重建**：`rebuild_quota(kv, date)` 用当日计量把日配额计数写回 KV（Redis 丢失后调用）。
6. **存储**：内存实现与 Postgres 实现（迁移 `0005_metering`，只追加）。

## 不做什么
- 不接 trace 后端、不做告警（spec §5.11 本期不做）；Web 面板归 F26。
- 事件类型 `human_request`、`violation` 由产生它们的 Feature（F05/F12/F25、F27）写入；本 Feature 只统计。
