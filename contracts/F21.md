# F21 Contract：确定性业务组件

> 状态：已写，按用户 2026-09-29 授权直接实现、事后统一验收 ｜ 类型：最小 ｜ 里程碑：M1 ｜ spec：§3.3、§2.3、G4、G7、G8 ｜ 依赖：F03、F06、F07

## 目标
数字与写操作全部由代码产生（spec §3.1 原则 2）：影响分析、比价、策略决策、等级汇总、采购执行都是确定性组件，产出带依赖的 Artifact，LLM 只能引用、不能改。

## 做什么（`src/business/`）
1. **影响分析** → `ImpactReport`：在环境状态的内存副本上（不影响真实运行，同 F03 预演）计算
   - 每颗料的供需时间线：可用 = 在库 + 按预计到货日累加的在途；需求 = 未开工工单按开工日累加；得出**缺口数量**与**首次缺料日**；
   - 不干预情况下的前推：各工单预计开工日、停线天数，各订单预计延期天数；
   - 可按范围过滤（料号、运单、工单、订单），数字全部由代码算出。依赖：环境当日状态（外部引用 `env:<运行>`，版本 = 模拟日，有效期按配置）。
2. **Sourcing** → `SourcingQuote`：输入是**需求列表**（多缺料预留，§1.7）；经 F07 代理层查报价（缓存、配额、留档、注入照常）；每条报价附到货日推算（有货：今天 + 备货 + 运输天数，来自环境分销商参数）；来源不可用时部分成功并写明缺失；依赖为各报价的留档记录与有效期。
3. **Policy** → `ProcurementDecision`：规则与权重全部来自 `config/policy.yaml`（G7）：AVL / 禁用分销商过滤、须能满足数量、单张采购单金额上限；按价格、到货日、库存余量加权打分，**打分过程逐项写入 Artifact**；同分按分销商名确定性取舍；无可行报价时决策为"无可行报价"并写明原因。
4. **等级汇总器**：按品类比对清单配置（`config/checklists/*.yaml`，mock 策略，§1.3）与 Verifier 逐项结论（满足 / 不满足 / 证据不足）算出 A / B / C 与理由；Verifier 本身归 F23。
5. **Procurement 执行器**：唯一能写采购数据的组件。
   - 建草稿 → `PODraft`：内容由代码从被引用的 Decision 字段生成（写操作只接受 Artifact 引用，§5.5），记下所依赖报价的留档号与数值快照；
   - 送审：写 `approval_requested` 事件（绑定草稿内容哈希）与 `human_request`（主管）；
   - 提交：幂等键 = 案子 + 草稿 ID + 草稿内容哈希，写入环境（F03），写 `po_submitted`。
   - 每个动作前调用**门控挂点**；本 Feature 自带最小门控（被引用 Artifact 必须有效、Decision 可行），证据门控、审批令牌、提交前重校验由 F12 接入同一挂点。
6. **接入 Runtime 与工具层**：前三个组件注册为 F09 的代码执行者（`dispatch_task` 增加可选 `params` 给代码组件传结构化参数）；执行器以"采购"Server 的三个写工具暴露（参数只收 Artifact 引用），白名单与 S1 限定归 F11/F22。代码组件可返回额外依赖（外部数据引用）。
7. **消融开关**：本 Feature 组件是"代码替 LLM 算数"的底线，不设消融开关（spec §0.3 的消融对象是 Harness 组件；单 Agent 等对照配置归 F28）。

## 不做什么
- 证据门控、审批令牌签发与校验、提交前重校验（F12）；意图 / 完成两步写与重放恢复（F15）；Monitor 与开案（F10）；Verifier、替代检索（F23）；上报计划员的人工流程（F05/F25）。
- 联合优化（§1.7）、真实分销商调用。
