# F37 Contract：人工决策、受控写入、发送账本与 WhatsApp/飞书渠道

> 状态：草案，等待 F41 ｜ 类型：深度 ｜ 里程碑：M3 ｜ spec：§0.3、§2.7、§2.8

## 目标

把图中的“动作分级与人工边界”“审批发送”“渠道事件”实现为同一条不可绕过的受控副作用链，覆盖 CRM 更新、采购提交和消息发送。

## 2026-10-10 架构约束

Proposal、Approval、Execution、SendLedger、渠道 webhook 验证及执行 Adapter 均属于 Python API/Worker；Next 只呈现审批收件箱并转发人工决定。渠道回调不能经 Next Route Handler 直接写 SQL，必须进入 Python 的验证、幂等和 Trace 链。

## 做什么

1. 统一 Proposal、Approval、Decision、Execution、SendLedger：提案绑定内容哈希、目标版本、组织、scope、风险、证据、有效期和幂等键。
2. 人工可批准、拒绝、要求恢复；批准签发不可由模型构造的短期令牌。所有 R1/R2 执行前重校验对象版本、角色、opt-out、service revision、证据和草稿哈希。
3. CRM 更新、采购草稿/提交分别复用既有门控；写操作失败/过期转为反馈和重规划，不能静默重试为成功。
4. WhatsApp Adapter：受控接收客户事件、创建/关联会话和回复提案；发送仅从已批准 SendLedger 执行。
5. 飞书 Adapter：加密 inbox/outbox、内部协作事件和 SQL Job；它不能代表客户渠道、不能绕过客户发送审批。

## 不做什么

- 不执行真实 WhatsApp/飞书连接、读取真实会话或发送消息，除非用户另行授权。
- 不永久授权某个 Run；不允许 Agent 直接调用 Adapter 的发送接口。

## 验收证据

| 命令/检查 | 通过条件 |
|---|---|
| 离线测试 | 未审批、过期、内容变更、权限变化、opt-out、重复投递均不能发送/提交；批准后恰好一次执行并写账本；恢复产生新提案。 |
| 真实集成（需授权） | 每个获授权渠道在隔离测试账号完成一入站、一草稿、一人工批准、一出站，审计和 send ledger 可核验。 |
