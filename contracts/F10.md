# F10 Contract：事件接入与案子管理（M1 薄版）

> 状态：已写，按用户 2026-09-29 授权直接实现、事后统一验收 ｜ 类型：深度② ｜ 里程碑：M1 ｜ spec：§5.2、§3.3 Monitor、A1/A8/A9 ｜ 依赖：F06、F09、F21

## 目标
所有输入统一为带实体键的事件（spec §5.2）；由代码决定投递给哪个案子、要不要开案、并入哪个案子、何时关闭；多案争用同一批供应时先到先得并反馈冲突。接到 F09 调度循环的路由挂点上。

## 做什么（`src/cases/`，配置 `config/cases.yaml`）
1. **环境事件补实体键**：`env_day` 事件的实体键补上料号（到货运单、发货采购单、开工 / 停线 / 完工工单所需的料）、板，便于订阅命中。
2. **Monitor（代码）**：每个模拟日对当日环境状态跑影响分析（F21），每颗缺料生成 `monitor_shortage` 事件（料号、缺口、首次缺料日、涉及工单；实体键含料号与工单；`caused_by` = 当日 `env_day`，F04 的异常事件接入后改指向异常事件）。去重键 = 料号 + 缺口 + 首次缺料日，同样的缺口不重复报。
3. **订阅**（从日志投影，代码维护）：案子的订阅集 = 开案实体键 ∪ 目标料号 ∪ 本案提交的采购单与分销商（`po_submitted`）∪ 本案 Artifact 外部依赖中的料号（`quote:<分销商>:<料号>`）。
4. **路由**（`CaseRouter`，Scheduler 的 router 挂点）：
   - 当日新事件（环境、Monitor、人工决定 `human_decision` / `approval_granted`、用户消息）的实体键命中某个未关闭案子的订阅 → 写 `event_delivered` 并唤醒该案子；人工事件直接唤醒其所属案子。
   - 未命中任何案子的 `monitor_shortage` → 代码开案（不交给 LLM）：**同源合并（A8）**——沿 `caused_by` 追到根因，同一根因的缺料合成一个案子、每颗料一个目标；根因已有未关闭案子时写 `case_target_added` 并入；开案模式 S1、目标文本由配置模板生成。没有缺口的环境事件只记日志。
   - 用户中途插话：写 `user_message` 并返回"本期不支持中途修改"（事件类型保留），不唤醒。
5. **目标与关闭**：每个目标有自己的状态（缺口仍在 / 已消除）；某案子全部目标缺口消除，且本案提交的采购单都已到货，才以 `resolved` 关闭（提交采购单不算完成）；写 `target_resolved` 与 `case_closed`。
6. **软声明（A9）**（`claims.py`）：Policy 决策选中报价时由代码登记 `supply_claimed`（案子、料号、分销商、数量、当时可用量）；其他未关闭案子对同一批供应的声明加上本次超过可用量 → 本次声明判冲突：写 `claim_conflict` 给后来的案子并 `human_request` 通知采购员；先到先得，不做联合优化。F12 草稿门控加一条：所用供应须有本案未冲突的声明。
7. **消融开关**：`same_source_merge`（false 时每颗缺料单独开案，A8 对照）、`supply_claims`（false 时不登记、不判冲突、草稿门控不查声明，A9 对照）。

## 不做什么
- F04 情景注入与其异常事件（本 Feature 的根因在 F04 前就是当日 `env_day`）；预期与偏差比对、反馈卡片（F14）；并发执行（F09 已定顺序执行）。
- 案子中途修改目标（用户插话）；多案联合优化（§1.7）。
