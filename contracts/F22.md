# F22 Contract：编排者（M1 薄版）与 Runtime 装配

> 状态：已写，按用户 2026-09-29 授权直接实现、事后统一验收；工具收敛方案经用户 2026-09-30 确认（合并同类工具） ｜ 类型：深度 ｜ 里程碑：M1 ｜ spec：§2.1、§2.2、§2.3、§2.5、§2.6、§2.7、§3.2、§3.6 ｜ 依赖：F09、F12、F21

## 目标
编排者在节点库里动态组合完成请求：路径由模型规划，底线由代码强制（路由定节点集合、计划校验、固定模板兜底、目标修订须采购员确认）。同时把 F10–F20 的可选组件装配成一套完整 Runtime。

## 工具收敛（用户确认：合并同类工具，每执行者 ≤ 8 个，spec §5.4）
编排者专用的三个合并工具（原细粒度工具保留给代码组件与测试）：
- `env_lookup(kind=inventory/purchase_orders/shipments/work_orders/orders, …)`：合并 5 个环境只读查询（R0）。
- `po_action(action=draft/request_approval/submit, …)`：合并 3 个采购写工具，风险级取最严 R2（只在 S1、只给编排者），门控按动作照旧逐一生效。
- `request_human(kind=goal_revision/planner/memory, …)`：合并目标修订、上报计划员、提议记忆三个交人处理的 R1 提议。
编排者工具集（配置 `config/orchestrator.yaml`）：S1 = dispatch_task、write_plan、env_lookup、ask_user、request_human、po_action、escalate_to_human、end_segment（8 个）；S3 去掉 po_action（7 个）。

## 做什么（`src/orchestrator/`）
1. **路由**（§2.1）：Monitor 开的案子由代码定为 S1；用户请求由 LLM 函数归类（S1 / S3 / 意图不明 / 超出范围，结构化输出），意图不明则反问、超出范围则拒绝，结果写 `case_routed` 并按模式开案。**模式决定节点集合**：派发时执行者不在当前模式节点集合里直接拒绝（S3 没有比价、决策、采购写入节点），与 F11 的工具可见性一起构成硬边界。
2. **任务图**（§2.2）：控制工具 `write_plan(tasks=[{id, executor, task, depends_on, inputs, reason}])` 产出 `Plan` Artifact（每个任务带一句理由，F16 计划分区展示，派发时可带 `plan_task` 以投影任务状态）。已有计划时再写即重规划（案子迁入规划中再回执行中，计入重规划预算）。
3. **计划校验**（§2.7，代码）：任务号唯一；执行者在当前节点集合且已注册；依赖存在且无环；输入引用的 Artifact 存在；按配置的节点单价估算 LLM 调用数不超过案子剩余预算。不合格写 `plan_rejected` 并返回原因；同一案子连续被拒达配置次数 → **退回该模式的固定模板计划**（配置），写 `plan_fallback`。
4. **固定模板**（§2.7、§3.6 对照组）：模板计划同时是 Eval 的"固定模板"对照配置；`TemplateDriver` 用代码按模板依次跑代码节点并按决策逐料建草稿、送审（不用 LLM、不重规划、不修订目标）。
5. **两级目标修订**（§2.5）：策略调整由编排者自己写进计划理由；目标修订经 `request_human(kind=goal_revision)` 写 `goal_revision_proposed` 并通知采购员（H4），`GoalDesk.confirm` 后写 `goal_revised`（案子卡片显示新目标，并按 F14 必须重规划唤醒），驳回写人工决定；未确认前按原目标继续。
6. **Runtime 装配**（`assembly.py`）：一处把各组件接好——Server（环境、分销商、留档、编排控制、采购、datasheet、知识库 B）、权限、重试熔断、注入计划（可选）、模型适配层、执行者循环、派发器（代码节点 + 已注册 LLM 节点）、活跃段（F16 上下文 + 记忆分区 + 编排者 Skill）、升级、案子路由（反馈循环、知识库同步）、证据门控（审批令牌、软声明、datasheet 刷新）、采购执行器；启动时做两步写恢复并记运行清单；`run_day()` 推进一天。消融开关全部取 `config/harness.yaml`。
7. **消融开关**：`plan_validation`（false 时不校验计划、不退回模板，对比动态编排的底线作用）。

## 不做什么
- 子 Agent 与 LLM 函数本体（原料画像、替代检索、Verifier、Resolver、Explainer 归 F23）；S3 问答的结论输出与引用校验路径（F24）；模拟人工应答（F05）；Web（F25）。
- 本 Feature 用脚本模型验证编排逻辑，不做真实模型调用。

## 验收证据
| 命令 | 通过条件 |
|---|---|
| `make check` | 离线测试：合并工具与原工具结果一致、po_action 各动作门控照旧；S1 编排者 8 个工具、S3 看不到 po_action；S3 案子派比价节点被拒；用户请求路由 S1 / S3 / 反问 / 拒绝；合格计划产出 Plan 并在上下文展示任务状态；不合格计划（未知节点、依赖成环、超预算）逐条给原因，连续被拒退回固定模板；关 `plan_validation` 不校验；目标修订未确认前目标不变、确认后卡片更新并唤醒；固定模板驱动器跑通 A1 缺料：影响分析 → 比价 → 决策 → 逐料草稿 → 送审；装配出的 Runtime 用脚本模型跑完"开案 → 编排者写计划 → 派代码节点 → 建草稿送审 → 结束本段"，启动恢复与运行清单都在 |
