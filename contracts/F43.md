# F43 Contract：在途事实一致性——到货明细、库存快照与缺料投影的权威来源和对账

> 状态：Contract 草案（未启动）｜类型：深度｜里程碑：M3｜spec：§3、§3.1、§5

## 问题

F39 同时保存库存快照的 `inventory_position.in_transit_qty` 和逐笔的 `supply_receipt`。当前没有来源、库位或关联事实可证明二者是否覆盖同一批在途货。为避免重复计入，F39 的精确缺料投影在发现非零且无法解释的聚合在途量时返回 `unknown`。持续补货料件因此可能长期无法得到精确投影。

## 启动前提

- F39 已完成真实 PostgreSQL RLS 与 API 端到端验收。
- F42 Harness 已完成其 Contract 验收。
- 用户在启动本 Feature 时选择以下数据语义之一；本草案不预先替用户作选择。

## 待选择方案

1. `supply_receipt` 是预测在途的唯一权威来源；库存快照中的聚合在途量保留为原始信息但不参与精确预测。
2. 聚合在途量仅表示尚未建立 receipt 明细的在途货；两者必须结构性互斥，并有写入校验。
3. receipt 明细是唯一权威，聚合在途量改为由 receipt 派生的展示值；需定义目标库位与历史迁移策略。
4. 两个来源均可独立存在；增加来源标识、外部引用、目标库位及显式对账/分配记录，只让语义明确或已对账的事实参与精确投影。
5. 在上述方案落地前，输出明确标记为保守风险日期或范围的结果，不将其称为精确首次缺料日。

## 实现范围（用户选择后再细化）

- 以 PostgreSQL migration 演进事实模型；不改写或伪造历史事实。
- Python 确定性投影只使用语义已定义的输入，保留未知与对账失败原因。
- 为组织、来源、库位和跨来源关联建立 RLS 约束与真实 PostgreSQL 负面测试。
- API/Workbench 明确区分精确预测、保守风险与未知；Harness 只读取已标注语义的结果，不能自行推断或修复数量。
- 补离线单元测试、真实服务 migration/RLS/API 集成测试，以及可审计的历史数据处置说明。

## 边界

- 本 Feature 不让 Agent、模型或浏览器直接修改供应链事实。
- 不连接真实 ERP、供应商或采购执行器；真实外部同步另需用户按 G5 授权。
- 不把不一致的数值“猜测为相等”，也不把保守风险结论标为精确缺料日。
- 当前只记录待办：在用户确认方案前，不修改 F39 的计算、schema、API 或验收状态。
