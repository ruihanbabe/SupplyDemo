# MVP PRD：电子制造物料保障 Agent

版本：0.1，2026-09-09。业务目标和技术范围来自用户确认；带“建议”的规则待评审后冻结。地区与业务系统见 [Q1/Q2](README.md)。

## 1. 产品目标与用户

采购员收到板卡备料需求后，能够查明缺料、查看可追溯的供应信息与技术资料，在人工批准后创建业务系统中的采购草稿。生产计划员查看物料就绪情况；工程核验人员处理型号和候选料歧义。个人演示允许一人切换角色，但权限仍由服务端校验。

生产需求只含产品版本、数量和需求日期，不安排设备、工序或人员。供应商库存不代表企业内部库存，供应商交期不等于承诺到厂日期。

求职证据：统一执行与权限、持久任务恢复、跨来源映射、定时触发、人工审核、来源约束的知识消费、可回放评测。不能以自称使用某知名 Harness 架构代替实现证据。

## 2. 范围

包含：人工提交需求；内部库存风险定时扫描；用料与库存计算；同型号供应查询；源 BOM 候选核验辅助；采购方案与审批；执行前复核；ERP 或业务服务草稿创建与核对；UI/CLI/定时任务统一入口；有界子任务与单 Agent 基线。

排除：完整排产、真实供应商下单付款、任意替代料自动批准、自动需求预测、多租户、完整收货结算、自动承诺交付；RAG／向量检索、规格书正文解析、带来源 Wiki 与技术卡片（MVP 不做，见 `DECISIONS.md`）。第二业务场景属于后续可迁移性验证，不阻塞第一场景。

## 3. 用户流程与功能编号

| 编号 | 用户行为／系统行为 | 可观察结果 |
|---|---|---|
| FR-01 | 提交产品版本、数量、需求日期 | 生成持久任务，缺字段则请求补充 |
| FR-02 | 读取 BOM、物料映射、库存及已分配记录 | 逐行需求与缺口；注明未知项，保持源行追溯 |
| FR-03 | 查询已选供应商的同型号供应 | 身份、包装、数量阶梯、币种、时间及缺失字段可见 |
| FR-04 | 核验候选型号身份与差异 | 输出候选间可证差异与身份状态；证据不足转人工核验，不做规格书正文检索 |
| FR-05 | 生成版本化建议 | 列出缺口、采购数量、成本口径、风险与未解决项 |
| FR-06 | 人工批准、驳回或要求修改 | 保存服务端审核记录；更改方案生成新版本 |
| FR-07 | 执行前核对并创建采购草稿 | 返回草稿标识及核对结果；不提交或付款 |
| FR-08 | 定时扫描触发风险任务 | 同一风险不重复创建；变化形成新事件／版本 |
| FR-09 | 暂停、故障、关闭 UI、服务重启 | 可恢复任务与审计，不重复产生副作用 |

## 4. 建议业务规则

BR-01：只有已核验为单件用量的行才能乘生产数量。数量口径不明或单位无法转换的行待核验，不参与生产需求展开。

BR-02：首版使用显式选定的一个候选满足一条用料；多个候选不累加，源候选关系不自动成为技术批准。后续若拆分候选供货，应另定数量分配规则。

BR-03：同一已批准物料的总需求 = 已选用料的单件用量 × 生产数量后汇总。计算使用精确数值类型；首版默认不加损耗，不能默默猜损耗率。

BR-04：需求日期前可分配量 = 可用实物库存扣除其他需求占用 + 到期前已确认且未分配的在途量。隔离／待检库存不计入。缺口 = max(0, 本需求未满足量 - 可分配量)。已满足量、库存占用和在途分配需有唯一关联，禁止重复抵扣；无到货日期的在途列作不确定项。

BR-05：建议计算不会自行修改库存或建立真实预留。多订单同时建议时提示资源竞争，执行前重新检查。若要承诺库存分配，必须另实现事务分配契约。

BR-06：报价按地区、币种、供应商商品、包装、数量和采集时间标识。金额按阶梯、最小起订量与倍数计算；未知税运费明确排除，不声称到岸总价。不同币种不自动混合比较。无价格、库存未知或交期不明，不伪装为完整报价。

BR-07：首版建议采购员手动选择方案；排序可按满足身份及数量条件后的已知商品金额。没有交期证据不得声称满足交付日期；只有一个供应来源时标为单源方案。

BR-08：批准绑定方案内容哈希、版本、报价证据、业务快照和动作范围。首版建议不设自动容差：供应商、商品、数量、金额或关键条件改变需重新批准；无需变化的刷新可保留审批，但必须保存复核证据。报价有效期是本地策略，不能冒充供应商保证。

BR-09：驳回进入 rejected；请求修改生成新版本；超时进入 approval_expired 或明确停止，绝不自动批准。无人处理的定时任务不连续复制。审批期限和提醒频率在数据策略阶段配置。

BR-10：混合已解决／未解决用料时，允许显示部分分析，整单不能标为就绪。首版建议阻止整单执行；部分采购必须让用户明确选择子集并形成独立审批范围。

BR-11：草稿按逻辑动作键去重。写入结果未知进入 reconciling，先查询核对；无法查明时请求人工处理。不能把 Redis 锁或一次查询后创建视作跨系统 exactly-once 保证。

## 5. 状态与执行设计约束

候选状态：created → analyzing → needs_input / awaiting_approval → revalidating → executing → reconciling / completed；另有 rejected、approval_expired、failed、cancelled。状态表和合法迁移由后续 ADR 固定。

所有状态与审批由持久存储承担；Redis 可以缓存与协调，不能独自保存恢复所必需事实。已发出的外部写入即使任务取消仍须核对结果。

用户请求和定时事件通过同一 Runtime 权限链；自动触发默认只读分析，草稿写入需审批。模型不能通过任意 HTTP、SQL 或通用执行工具绕过业务动作。子任务预算从父预算扣除，权限不能扩大。

Graph 表达依赖与等待；供应查询和技术核验可独立执行，汇总节点校验所需证据。Loop 用于有界的查询和修正；算术与硬规则由程序实现。多 Agent 是否提升质量与效率由基线比较证明。

## 6. 界面

元件技术信息在运行时由供应查询工具返回，不预先建库、不做正文检索；未核验身份标明状态。

界面至少包含需求提交、风险清单、任务详情、来源查看、审批对比与草稿结果。展示业务状态和需要用户做的决定；内部框架名称不占据主要用户流程。

## 7. 验收出口

FR-01 至 FR-09 均关联 [eval 清单](ACCEPTANCE-EVAL.md)。必须有一个固定端到端任务完成真实业务 API 的草稿创建和读回；供应查询须有授权实测记录，模拟演示不得冒充真实供货。

必须覆盖：审批前写入被阻止、审批失效、重复触发、写入响应丢失、重启恢复、预算耗尽。硬性副作用与权限检查不允许以平均质量分抵消失败。

性能、模型预算、延迟和恢复时间先测基线后定量冻结；本稿不编造成功率或收益。
