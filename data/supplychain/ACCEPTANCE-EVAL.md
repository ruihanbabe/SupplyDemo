# 验收与 eval 设计

日期：2026-09-09。以下均为计划用例，尚无产品实现、eval runner 或执行成绩。来源是现有数据、PRD 规则与设计的故障注入。

## 1. 判定原则

业务硬规则由独立断言判定；语言表述使用证据覆盖和人工复核，不让 LLM 单独裁定权限与写入正确性。模型不得看到隐藏预期答案。真实数据可作为开发集；保留独立变体作为留出集，避免仅背诵当前 162 条记录。

每例需保存：case_id、类型、来源文件哈希、记录 ID、前置条件、触发输入、故障脚本、expected_state、required_evidence、forbidden_actions、副作用计数、预算、判定器版本。下面的种子尚未物化为完整 fixture。

## 3. 执行层次与门槛

1. 静态契约：输入输出 schema、引用完整性、状态合法迁移和模块依赖检查。
2. 离线测试：固定数据与 mock，覆盖身份、算术、权限、预算；不访问供应商。
3. 集成故障注入：本地真实数据库/Redis/目标业务服务，注入超时、进程终止、并发与响应丢失。
4. 授权端到端：真实供应只读接口 + 自己控制的业务系统草稿写入；记录版本、地区、时间和结果。

硬门槛：固定案例的越权写入、重复草稿、伪造身份、无证据关键结论均为0；所有硬案例必须通过。其余回答质量、引用准确率、成本、工具次数、延迟按案例分别报告，样本小不外推生产收益。

单 Agent 和多 Agent 使用相同工具、数据、预算与任务集，重复执行并报告方差及失败例；不预设多 Agent 一定更优。开发和留出评测拆分；网络变化场景与固定离线回放分开报告。

当前只完成用例设计与种子引用检查。后续 runner、故障注入器、阈值及人工标注仍待开发，不存在“28例已通过”的结论。
